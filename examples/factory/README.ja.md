# 工場：設備異常と品番の不具合履歴を交差させる

リポジトリのルートで `pnpm demo:factory` を実行します。架空の MES・WMS と、メモリ上のオントロジーストアを使い、毎回初期状態から始めます。

9月8日の点検で PRESS-1 に圧力異常が見つかりました。品質担当は、この設備で9月6日に製造したロットを調べます。製造日の範囲は調査の前提として与えられています。一方、製品カタログには品番 P-A で過去に圧力由来の品質問題があったと記録されています。両方に該当するロットを優先確認し、出荷済みの数量と顧客を辿って、連絡・再検査の検討タスクを作ります。

不具合履歴は以前のロットに関するもので、その時から製品仕様は変わっていない前提です。1ロットは1品番に対応します。カタログの `pastPressureIssue` は過去の知見であり、今回のロットの不良判定ではありません。9月7日の出荷前検査は合格しており、現在の製品不良は未確定です。設備の故障開始時刻を推定する例でもありません。

グレーはソース由来、オレンジはオントロジーが所有する状態です。全オブジェクト型・リンク型を示し、属性は抜粋しています。[編集用 SVG](./assets/ontology-overview.ja.svg)。

[`demo.ts`](./demo.ts) は Equipment → Lot と Product → Lot の独立した2経路を辿ります。Runtime の filter・pivot・集合演算を直接組み合わせ、各操作の入力と結果の型・ID・件数を表示します。

| 段階 | 結果 |
| --- | --- |
| 経路A：圧力異常の設備を filter、ロットへ pivot、製造期間で filter | PRESS-1 → **A = {L1, L3}** |
| 経路B：別途カタログを過去の圧力由来不具合で filter、ロットへ pivot | P-A → **B = {L1, L2, L4}** |
| ロット集合の積集合で優先確認対象を選ぶ | **A ∩ B = {L1}** |
| A から優先対象を引き、残る調査範囲を保持する | L3 は引き続き調査対象 |
| L1 から出荷明細へ pivot | SL1・SL3・SL5 |
| 出荷へ pivot し、出荷済みを filter | S1・S2 |
| 出荷済みの出荷から、含まれる全明細へ pivot | SL1・SL6・SL3・SL4 |
| 出荷済みの全明細と、優先ロットの明細との積集合を取る | SL1・SL3 |
| 出荷済みの出荷から顧客へ pivot | C1（Aoba）、重複を除いて1件 |
| 残った明細の数量を合計する | **10 + 20 = 30単位** |
| 同じ根拠明細のIDでタスクを作る | CONTACT-C1 と5本のリンク |

L1 は設備側の条件と品番の履歴の両方に該当します。L2 は同じ品番 P-A でも9月5日製造、L4 は同じ P-A でも別設備 PRESS-3 の製造です。L3 は対象設備・期間に該当しますが、品番 P-B に圧力由来の不具合記録がありません。**L3 も影響候補には残ります。履歴がないことは安全の根拠ではありません。** この積集合は優先順位を付けるもので、全影響対象や原因を確定するものではありません。

C1 は L1 の出荷 S1・S2 から見つかり、2経路が合流しても1件になります。C2 が受け取った L2 は期間外で、C3 宛ての L1 の10単位は未出荷です。後半の積集合では、優先ロットの出荷済み明細だけを残します。未出荷の SL5、継続調査する L3 の SL4、別設備の L4 の SL6 を除き、SL1・SL3 の合計は30単位になります。L1 全体では未出荷分を含め40単位、S1・S2 全体では他のロットを含め55単位です。出荷明細の粒度で数量を求め、その同じIDを Action の根拠に渡します。

担当者は `createContactTask` を実行します。Action は圧力異常、製造期間、ロットに対応する品番の現在の履歴、顧客、出荷済み明細の根拠を再検査し、オントロジー所有のタスクと顧客・設備・ロット・明細へのリンクを原子的に作ります。保存したロットから Product にも戻れるため、両方の経路を確認できます。メッセージ送信や出荷・ロットの状態変更は行わず、残る調査を完了扱いにもしません。再インデックス後もタスクと根拠リンクを保持しますが、リンク先のソース内容を過去のまま固定するものではありません。

## コードと MCP

[`demo.ts`](./demo.ts) から読み、Action とそのルールは [`ontology.ts`](./ontology.ts) で確認できます。`fixtures.ts`・`integrate.ts` が既存のソースの事実を供給し、`runtime.ts` がモデルの読み取りとランタイムを接続します。ソースへの書き戻しは [orders](../orders/ontology.ts)、候補検索の Function と割当は [hospital](../hospital/README.ja.md)、共通項の調査は [finance](../finance/README.ja.md) で扱います。

`pnpm mcp:factory` で起動します。リポジトリのルートからは次でも接続できます。

```sh
claude --strict-mcp-config --mcp-config examples/factory/.mcp.json
```

モデルから読み取り・pivot・集合演算・集計のツールと `create_contact_task` を生成します。エージェントは自身のコード実行環境で取得済みオブジェクトを絞り、選んだIDを次のツールへ渡します。`pivot_produced_on` と `pivot_product_lots` で2経路のロット集合を得て、`intersect_lot` で優先対象を選び、`subtract_lot` で残る調査対象を保持します。出荷を辿った後は `intersect_shipment_line` で出荷済みの根拠を残し、数量を合計して Action に渡します。`scenario.test.ts` の MCP テストでこの流れを確認できます。利用者に代わって探索を完了する Function はありません。契約は [IMPLEMENTATION.ja.md](../../IMPLEMENTATION.ja.md) にあります。単一の書き込み元と、判断に関係する全資源が見えることを前提とします。
