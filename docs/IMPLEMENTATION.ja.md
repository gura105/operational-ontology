# 実装ノート

[README](./README.ja.md) はパターン、デモ、実装の範囲を紹介します。この文書は、この実装の API とランタイムの振る舞いを説明します。共通仕様の動作・型・MCP の検証は [`tests/`](../tests/)、各例のシナリオテストは `examples/*/scenario.test.ts` に置き、`pnpm test` で両方を実行します。

アクション実行の拒否は `{ ok: false, error: { code, message } }` として返り、監査されます。プログラムやストレージのエラーは例外になる場合があり、書き込み経路では後述のとおり記録します。クエリのエラーは、アクションの拒否ではなく例外です。

## コードの分担

`core.ts` は、モデルの定義、書き戻しの契約、`Runtime` の順に並びます。`Runtime` 内では、インデックス、読み取り、Action の実行、監査の読み取り、内部ヘルパーを順に追えます。取得済みの集合だけを扱う純粋な操作は `query.ts` に置きます。

| ファイル | 責務 |
| --- | --- |
| `core.ts` | 定義用の関数、インスタンス、編集プランと、それらを読み取り・実行・保存・監査する Runtime。 |
| `query.ts` | 取得済みの集合・集計に対する純粋な操作と、呼び出し側が渡す述語の適用。 |
| `mcp.ts` | モデルからツールを生成し、入力を同じランタイム操作へ渡す。 |

## インスタンスと走査

実行時のオブジェクトは `{ type, pk, properties }` という読み取り時点のスナップショットです。同一性は `(type, pk)` で決まります。`pk` は宣言された主キーの値なので、プロパティ名が `id` でなくても扱えます。業務プロパティに `type`・`pk`・`properties` という名前があっても、内側に入るため衝突しません。スナップショットを書き換えてもストアは変わりません。

`get` はインスタンスまたは `undefined` を、`search`・`traverse`・`pivot` は `ObjectSet` を返します。visibility、オブジェクト用の述語フィルタ、アクションのコンテキスト、`meta.target` はインスタンスを受け取ります。`modify` の変更内容、`create` の data、インデックスに渡す行には業務プロパティを直接指定します。`defineAction(objects, …)` は `object` の名前から `ctx.object` を、パラメータスキーマから `ctx.params` を型付けします。`modify(instance, changes)` は編集を記述するだけで、書き込みません。すべての編集内容を実行時に検査します。

注文デモでは、リンクのどちら側からも走査できます。

```ts
const hq = { actor: 'user:hq' }
const customer = rt.get('Customer', 'N-C01', hq)!
const orders = rt.traverse(customer, 'customerOrders', hq) // ObjectSet、type === 'Order'
const customers = rt.traverse(orders.objects[0], 'customerOrders', hq) // ObjectSet、type === 'Customer'
console.log(orders.objects[0].properties.status)
```

入力の名前は文字列、操作の params と編集する属性は普通のレコードで受け取ります。モデル固有の名前・値・関係は実行時に検査します。

`get`・`search`・`call` にリテラルで名前を指定すると、戻り値の型が決まります。モデル定義の推論された型を保ってください。`OntologyDef` と明示的に注釈すると、具体的なスキーマの型情報は失われます。動的なオブジェクト名では属性値が `unknown` の共通インスタンス、動的な Function 名では `unknown` を返します。`traverse`・`pivot`・集合演算は共通の `ObjectSet` を返します。走査後に具体的な属性型が必要なコードでは、型の絞り込みやアサーションが必要です。アサーション自体は値を検証しません。

`traverse(source, linkName, { actor, direction? })` の始点には完全なインスタンスを渡します。方向はリンクの定義から決まります。

TypeScript のインターフェースでは `direction` は任意です。省略できるかは実行時に判定し、不可能な方向や、同じ型同士のリンクで方向が未指定の場合は拒否します。

| 始点の型が一致する端点 | direction | 実行時の行き先 |
| --- | --- | --- |
| `from` のみ | `forward`、省略可 | `to` |
| `to` のみ | `reverse`、省略可 | `from` |
| 両方 | `forward` または `reverse`、必須 | 同じオブジェクト型 |
| どちらでもない | 始点に対して無効なリンク | — |

上司から部下への `Employee → Employee` リンクなら、`forward` は部下、`reverse` は上司を取得します。

判定基準は定義上の型で、実データのつながり方には依存しません。one-to-many の逆方向でも集合を返し、`type` タグが行き先を表します。走査は `(type, pk)` を呼び出し元の actor で読み直し、両端の可視性を検査します。渡された properties はこの判定に使いません。始点が欠損・非表示なら、行き先の型を保持した空集合を返します。不正な始点の形、リンク、方向は例外です。

`pivot(set, linkName, { actor, direction? })` は各始点に同じ規則を適用し、行き先を重複排除します。入力が空でもリンクと方向を検査します。一度訪れた型へ戻っても、取得するのは現在の集合に関係するインスタンスであり、元の集合やその型の全件ではありません。

## ObjectSet・filter・集合演算・集計

`ObjectSet<O>` は `{ type, objects }`、つまり1種類のオブジェクト型と、そのインスタンス配列を持つ取得済みの集合です。空でも型を保持します。同一性は `(type, pk)` で決まり、重複は最初の要素を残します。`objectSet(type, objects)` で構築・検査できます。TypeScript ではタグと配列を readonly にし、タグと全要素の一致は実行時に検査します。任意の要素型 `O` は属性の型を表しますが、この一致を証明するものではありません。深い freeze ではなく、properties は読み取り時点の値で、集合操作の結果が同じインスタンス値を共有する場合があります。

`filter`・`union`・`intersect`・`subtract`・`aggregate` は、取得済みの値に対する操作です。actor を受け取らず、ストアを読みません。新しい入れ物を返し、ストアの更新や監査記録はしません。集合演算は同じ型同士だけで行います。和集合は左の要素と右だけにある要素の順、積集合・差集合は左の順と値を保ちます。鮮度の比較はせず、同じ ID の値は左を優先します。現在の状態が必要なら読み取りや Function を再実行してください。

```ts
const orders = rt.search('Order', { actor: 'user:hq' })
const pending = rt.filter(orders, (order) => order.properties.status === 'pending')
const large = rt.filter(orders, (order) => order.properties.total >= 10000)
const either = rt.union(pending, large)       // OR
const both = rt.intersect(pending, large)   // 集合同士の AND
const remaining = rt.subtract(orders, both)
```

`filter` は同期的な TypeScript の述語関数を受け取ります。`search` の任意の `filter` オプションも同じコールバックです。述語は副作用を起こしてはいけません。例外はそのまま伝わり、アクションの監査には記録しません。ランタイムは集合の形を検査し、比較・大文字と小文字・OR/NOT・nullや欠損値の扱いはコールバックに任せます。コールバックのロジックを属性スキーマで検査したり、純粋性を強制したりはしません。

日時は、examples では `Date.parse(...)` の値を比較し、UTCオフセットが異なる表記も時点として比較します。保存された属性は文字列です。

`aggregate(set, { groupBy?, sum? })` は必ず `count`、任意で1つの数値属性の `sum` を求めます。`groupBy` を省略すると集合全体を集計し、スカラー属性を指定するとグループごとに集計します。`aggregate(set)` だけなら全体の件数を返します。結果は次の2つを持ちます。

- `set`：各グループに属する入力オブジェクトの集合。
- `values`：グループの `key`（スカラー、全体集計なら `null`）、対応するオブジェクトの `pks`、`{ count: 2, sum: 5000 }` のような `metrics` を持つ行。

全体集計は空集合でも必ず1行を返し、その場合は `count` が0、指定した `sum` も0です。属性でグループ化した場合、空集合は0行になります。件数・合計はオブジェクトIDの重複を除いて計算し、複数経路で同じ対象に到達しても二重に数えません。

```ts
const total = rt.aggregate(pending, { sum: 'total' })
console.log(total.values[0].metrics) // 選んだ注文全体の件数・合計。key は null。

const grouped = rt.aggregate(pending, { groupBy: 'status', sum: 'total' })
const selected = rt.filter(grouped, (row) => row.metrics.sum >= 10000)
console.log(selected.values) // 選択された行。集計値は元の値を保つ。
const targets = selected.set // その行に属する Order の集合
```

集計結果への filter は述語で行を選び、対応するオブジェクトの和集合を残します。集計値は再計算しません。属性で絞りたければ `.set` を filter し、必要なら明示的に再集計します。0行になっても空の型タグ付き集合と空の `values` 配列を保持します。groupBy の属性が別の型の ID であっても、その型へ自動的に pivot はしません。

リンクを使う集計や独自指標はモデルの Function に置き、同じ `AggregationResult<O>` を返せます。例えば金融では、**取引**から求めた `senderCount`・`transactionCount`・`totalAmount` を、対象の**口座**集合に対応させます。`aggregationResult(set, values)` は有限の数値、グループキーの一意性、メンバーの参照を検査し、対応する集合を作ります。`metrics` は `Readonly<Record<string, number>>` です。列名を揃える責任は結果を作る側にあります。タイプミスや列の欠落は検査せず、存在しない列の参照は実行時には `undefined` になります。

行の `pks` は対象集合の ID であり、自動的に根拠レコードを意味するものではありません。根拠集合は Function の結果で集計と並べて返し、利用者が選んだ対象に対応するものを取り出します。集計はスカラー属性の optional・nullable・default を認識しますが、属性のnull・欠損値をキーにしたり合計したりすると例外になります。全体集計の `key: null` はグループ化しないことを表し、属性値がnullのグループではありません。空の `pks` を許すのも、この全体集計の行だけです。

## MCP のクエリ入力

モデルから `search_<type>`・`get_<type>`・`union_<type>`・`intersect_<type>`・`subtract_<type>`・`aggregate_<type>` と、`traverse_<link>`・`pivot_<link>` を生成します。

| ツール | 入力 |
| --- | --- |
| `search_<type>` | `{}`。このセッションから見える全オブジェクト。 |
| `get_<type>` | `{ <primaryKey>: value }` |
| `union/intersect/subtract_<type>` | `{ left: pks, right: pks }` |
| `aggregate_<type>` | `{ pks, group_by?, sum? }`。`group_by` を省略すると全体集計。 |
| `traverse_<link>` | `{ source: { type, pk, properties }, direction? }` |
| `pivot_<link>` | `{ source: { type, pks }, direction? }` |

生成スキーマはモデルの型・リンク・集計対象の属性を選択肢として提示します。同じ型同士のリンクでは、traverse と pivot のスキーマで `direction` を必須にします。

オブジェクトの集合は `{ type, objects }` で返します。サーバーは条件句・コールバックの文字列・任意のコード・SQLを受け取りません。エージェントは自身のコード実行環境で結果を絞り込み、選んだIDを次のツールへ渡します。コード実行に対応したクライアントが必要で、その実行環境はこのリポジトリでは提供しません。絞り込む前のオブジェクトをクライアントへ転送するため、大きな集合では転送量が制約になります。

MCPツールを呼び、JSONの結果を読み取る `call<T>` ヘルパーを使う場合の例です。

```ts
const orders = await call<ObjectSet>('search_order', {})
const pks = orders.objects
  .filter((order) => order.properties.status === 'pending')
  .map((order) => order.pk)
const customers = await call<ObjectSet>('pivot_customer_orders', {
  source: { type: 'Order', pks },
})
```

集計結果では、`.values` をローカルで filter し、選ばれた行の `pks` を重複排除します。そのIDをpivot・集合演算・集計へ渡し、集計結果全体をサーバーへ返してfilterすることはありません。集計値は分析時点のスナップショットです。各ツールはIDをセッションのactorで読み直すので、以前の結果に含まれていても、その後に非表示や欠損になったオブジェクトへのアクセスは認めません。Actionは現在の業務条件と根拠を独立して再検査します。候補の適合判定は引き続きモデルのFunctionとActionに置き、ローカルのfilterは利用者の調査上の絞り込みを表します。

[金融のMCPシナリオテスト](../examples/finance/scenario.test.ts)に、`call<T>` ヘルパー、ローカルでの日付・集計値のfilter、Actionまでの実行例があります。クライアントのコードから `query.ts` の純粋な `filterObjects` / `filterAggregation` を使えば集合の形を維持できますが、返されたJSONからIDを選ぶために必須ではありません。

## 可視性と呼び出し元の identity

`get`・`search`・`traverse`・`pivot` は `actor` を受け取ります。取得済み集合への純粋な操作では可視性を再検査しないため、別の呼び出し元へ値を共有する際の管理はアプリケーションの責務です。オブジェクト型に付けた省略可能な `visibility` 述語が、読み取りとアクションの対象を絞ります。見えないオブジェクトは存在しないものと同じ扱いで、`get` は `undefined` を返し、走査結果にも現れず、アクションの対象なら `TARGET_NOT_FOUND` で拒否されます。

認証は、actor の身元をランタイムの外で確立する責務です。認可を設ける場合は、オブジェクト型やアクションにポリシーを配置し、すべての消費者に同じ制約が働くようにします。その配置と、グループ・属性・ポリシー言語などの実現機構は別の設計判断です。事前条件は業務上の妥当性を検査します。権限と妥当性を分けて設計することは推奨しますが、別々の仕組みにすること自体はパターンの成立条件ではありません。

この参照実装は、ポリシーをモデルに配置して作用させるところを示します。認可をどこまで実装するかは各実装の選択で、ここでは `visibility` を省略可能とし、デフォルトを fail-open（全員に見える）と宣言しています。actor は自己申告の文字列で、ランタイムは認証や汎用のアクション権限機構を持ちません。可視性の指定を必須にするだけでは、身元を確認した利用者ごとの保護は実現できません。監査ログの読み取りは、visibility で絞らない管理者向けのビューです。

MCP の stdio 接続では、呼び出し元は1つの actor を共有します。`OO_AGENT=<name> pnpm mcp` は `agent:<name>` というラベルを付けるもので、認証ではありません。サーバーはモデルから読み取り・アクションのツールを生成し、ランタイムへ呼び出しを渡します。アクションの拒否は `{ error: { code, message } }` を含む MCP エラーになり、捕捉したランタイム例外には `INTERNAL` コードを使います。ローカルストアへのアクセスについては[トランザクションの所有権](#トランザクションの所有権)を参照してください。

## 名前付き操作の実行

`execute(actionName, params, { actor })` は Action を実行し、`call(functionName, params, { actor })` は Function を呼びます。どちらもモデルの入力スキーマで params を検査します。`execute` は成功・拒否を `ActionResult` として返し、未知の Action 名も `UNKNOWN_ACTION` として拒否・監査します。`call` は Function の戻り値を返し、非同期の実装なら Promise になります。未知の Function 名は例外になります。MCP のツール名を曖昧にしないため、Action と Function は異なる名前にする必要があります。

## アクションの実行

アクション定義の `preconditions` は必須です。条件がない場合も `[]` と明示します。業務ルールを備えたアクションが書き込みの入口なので、「条件なし」もモデルの作者が選んだ判断として定義に残します。

`execute(actionName, params, { actor })` は次の順で処理します。

1. params を検証し、actor の可視性ポリシーを適用して対象を読み込む。
2. 事前条件を順に評価し、最初の拒否理由を返す。
3. effects 関数から編集プランを得る。
4. コミットと同じコードでプラン全体をドライランし、ロールバックする。
5. プランを所有の宣言と照合する。
6. 空でない source-backed なプランをアダプタ経由で書き戻す。
7. ローカルの編集と監査エントリを1つのトランザクションでコミットする。

effects はデータとして変更を記述する純粋な関数です。`modify` はプロパティの変更、`create` はオブジェクトの作成、`link` / `unlink` は関係の変更を表します。source-backed なオブジェクトの作成には、更新と同じく write-back が必要です。アダプタが走る前に、スキーマ・オブジェクトの存在・多重度を検査します。1つの Action が配列パラメータを受け取り、複数の編集を原子的にコミットできます。別々の Action 呼び出しは、トランザクションも監査エントリも別々です。これらの編集はインスタンスを変え、モデルの定義はコードとして git でレビュー・版管理します。

## モデル定義の Function

モデルの `functions` に、`defineFunction({ description, params, run })` で名前付きの読み取り処理を登録します。`call` は params を検証して `run({ params, actor })` を呼び、コールバックにはスキーマから導く params の型が付きます。不正な入力・実装上のエラーは例外になり、呼び出しはアクションの監査ログに記録しません。MCP は同じ入力スキーマとセッションの actor を使うツールを生成し、`readOnlyHint` を付けます。非同期の結果は待ち、捕捉した例外は `INTERNAL` エラーとして返します。

Function の実装は読み取りに呼び出し元の actor を使い、書き込みなどの副作用を起こしてはいけません。事前条件・effects と同じく、これはモデル作者が守る契約であり、サンドボックスによる強制ではありません。Function は、特定の Action に対応しない業務上の読み取りにも使えます。

候補の評価と Action の事前条件は、モデル内の普通の評価関数を共有できます。Function が適合条件や変更予定を返し、Action は実行時点のインデックスに対して業務条件と編集プランを検査します。Function の結果は資源の予約や、編集プラン全体の妥当性の保証にはなりません。

具体例は、[顧客への影響と連絡タスク](../examples/factory/README.ja.md)、[候補評価と仮割当](../examples/hospital/README.ja.md)、[受取先の集計と調査ケース](../examples/finance/README.ja.md)を参照してください。探索で Action の根拠を見つける流れ、Function による候補評価や指標比較、Action による選択内容の再検査と保存を説明しています。根拠リンクが保存するのはレコードの同一性であり、ソースの内容を過去のまま固定したコピーではありません。

## Authority の検査

モデルは所有を 2 箇所で宣言します。オブジェクト型とリンクの `owned` が ontology-owned な状態に印を付け、アクションの `writeback: true` がその変更を source-backed と宣言します。ランタイムはすべての編集プランを `owned` 宣言に照らして分類し、アクションの宣言と矛盾するプランを拒否します。

| プランの内容 | アクションの `writeback` | 結果 |
| --- | --- | --- |
| source-backed な状態を変える | なし | 拒否：**`UNDECLARED_SOURCE_WRITE`** |
| ontology-owned な状態しか変えない | あり | 拒否：**`MISDECLARED_WRITEBACK`** |
| 両方の種類を変える（1 つの編集内でも、編集をまたいでも） | どちらでも | 拒否：**`MIXED_AUTHORITY`** |

各行の理由は次のとおりです。宣言なきソース書き込みは、ソース所有のデータをローカルで変えながらソースに届けない構成であり、性質 4 が禁じるものそのものです。宣言と裏腹の write-back は、プランの中にソースへ属するものが 1 つもありません。混在プランを拒否するのは、本実装がプランを丸ごとルーティングするためで、両方が必要ならアクションを分割してください（edit 単位のルーティングは未対応です）。

空のプランは境界のどちら側にも触れません。アダプタは呼ばれず、監査エントリだけがコミットされます。write-back を宣言したアクションにアダプタが構成されていない場合は、**`NO_WRITEBACK_ADAPTER`** で拒否されます。

検査の順序は、妥当性が先、authority が後です。プラン全体がまずコミットと同じコードでドライランされるため、ストアが受け付けないプランは、たとえ authority の境界もまたいでいたとしても **`INVALID_EDITS`** になります。

宣言された 4 つの答えそのものも、`Runtime.declarations` として実行時に列挙でき、テストで固定されています。

### Source-backed なオブジェクトの作成

`create(type, pk, data)` は型の所有権に従います。`owned: true` ならローカルで作成し、それ以外では `writeback: true` とアダプタが必要です。アダプタは既存の `create` 編集を受け取り、ソースにレコードを保存してから戻り、その後ランタイムがローカルにコミットします。Action の対象には引き続き、呼び出し元から見える既存オブジェクトが必要です。たとえば Customer を対象とする Action で、Ticket の作成と、その Ticket への source-backed なリンクの作成を順に同じプランへ含められます。

ID は `pk` と `data` の主キープロパティの両方に指定します。アダプタはその ID と指定されたソース属性を保持して保存し、ソースでの競合や作成拒否を例外として返す必要があります。ソースが採番した ID や置換値を返す仕組みはありません。各アダプタが対応する操作を実装します。orders デモの既存アダプタは、引き続き注文キャンセルだけに対応します。[作成のテスト](../tests/source-create.test.ts)では、実際の SQLite `INSERT`、リンク作成、ソースのトランザクションのロールバック、再インデックスを実証しています。

`owned: { property: default }` を持つ型では、`load()` と同じく、該当プロパティを `data` から省きます。ランタイムがその初期値をローカルで補い、アダプタには渡しません。owned 属性を明示的に指定すると、初期値と同じ値でも `MIXED_AUTHORITY` になります。その変更は別の Action で行います。作成された行の所有権はソースにあるため、その後のスナップショットで通常どおり置き換わり、後から加えた owned 属性の編集は既存のオーバーレイで保持されます。

## 失敗時のセマンティクスの詳細

宣言している順序は write-back 先行です。アダプタはローカルコミットより先に走り、システムオブレコードが拒否すればオントロジー側は何も変わりません。残るリスクは逆向きの失敗、つまりアダプタは成功したのにローカルコミットが失敗するケースで、これが起きると両システムは乖離します。このリスクを 3 つの仕組みが狭めています。

**不正なデータは境界を越えません。** アダプタが走る前に、編集プラン全体が「必ずロールバックされるトランザクション」の中で一度適用されます。コミットと同じコードによるドライランであり、実装がずれていく可能性のある第二のバリデータではありません。ストアが検出できる違反（スキーマ、多重度、リンクの端点）はすべて、何かがシステムオブレコードに届く前に拒否されます。アダプタは必要な入力を前もって、それぞれ自分専用のコピーとして受け取ります。検証済みのプランと、ランタイムがロードしたターゲットオブジェクト（`meta.target`）です。そのため、アダプタがオントロジーストアを読む必要はありません。

**監査ログは、どちら向きの失敗も記録します。** **`WRITEBACK_FAILED`** の拒否は、アダプタが見たプラン全体を記録します。ソース側の原子性はアダプタの契約でありこのランタイムの契約ではないため、アダプタは throw する前にプランを部分的に適用してしまっているかもしれないからです。逆向きの失敗は **`COMMIT_FAILED`** として、やはりプランを添えて監査されます。write-back 先行のアクションの後では、その編集こそが既にソースへ届いた内容だからです。どちらのエントリも照合の材料になります。

**「すべてのアクション試行は監査される」には、明示された限界があります。** 対象は、書き込みゲートに入り、このランタイムが完了まで観測できた `execute` の試行です。未知の Action 名も含みます。読み取り・Function 呼び出し・呼び出し側のトランザクションを理由に拒否された呼び出しは、このログに入りません。ソース更新とローカルコミットの間でプロセスが死ねば、編集も監査エントリも失われます。この隙間を塞ぐには pending-invocation の永続化された記録が必要ですが、本実装は持っていません。

書き込み経路の内側でのクラッシュは **`EXECUTION_CRASHED`** として監査されます。ストレージ障害、またはモデルコード（可視性述語、事前条件、効果関数）が throw した場合で、エラーはその後呼び出し側へ伝播します。

監査の書き込み自体が、失敗しうる箇所であってはなりません。JSON に直列化して復元すると値が変わる params は、モデルが走る前に **`INVALID_PARAMS`** として拒否されます。それでもログにエンコードできない値が残った場合は `$unserializable` プレースホルダとして記録します。欠損した監査エントリより、劣化した監査エントリの方がましだからです。

監査ログをオブジェクトグラフの外に置くのは、通常の業務オブジェクトと契約が異なるためです。業務編集を何もコミットしない拒否やクラッシュも記録し、エンコードできない値はプレースホルダに置き換えて記録を残し、ランタイム自身がアクションを経由せず追記します。通常のオブジェクトにすると、スキーマによる拒否やアクション経由の書き込みに例外が必要になるため、この実装では独立した管理者ビューとして扱います。

**事前条件と鮮度。** ルールが見るのは、インデックスされたスナップショットと適用済みのローカル編集です。ソースはインデックス後に変わっている可能性があり、ランタイム自身はソース側の不変条件を再検証しません。この境界への対応はアダプタの仕事です。デモの [ERP アダプタ](../examples/orders/erp-adapter.ts)はガード付き `UPDATE` を使い、その後出荷された注文のキャンセルを ERP 自身が拒否できるようにしています。

**並行編集。** アクションの実行もアダプタのインターフェースも同期的です。この例は単一の書き込み元を前提とし、ドライランからコミットまでの間に他のアクションが割り込まない構成です。非同期のアダプタや複数の書き込み元を扱うには、明示的な並行制御が必要で、ここでは実装していません。

**リトライ。** 冪等キーや重複排除はありません。`cancelOrder` は自身の事前条件でキャンセル済み注文を拒否しますが、すべてのアクションや外部への副作用を安全にリトライできる保証にはなりません。呼び出し元が指定するノート ID はローカルでの重複生成を防ぐ手掛かりになりますが、汎用のリトライ機構ではありません。

アクションのインスタンスを区別するのは、引数ではなく個々の実行試行です。同じ params で2回呼び出しても別々の試行であり、それぞれが監査の対象になります。params に呼び出し ID を持たせれば試行を関連付けられますが、重複排除にはその ID の検査・記録と副作用の実行をどう連携させるかも決める必要があります。ID をログに残すことだけでは、同じ操作の二重実行は防げません。

## トランザクションの所有権

ロールバックの責務は3つに分かれます。ソースのデータセットの版管理と巻き戻しはデータ基盤の仕事です。このランタイムは、アクションのローカル編集と監査エントリを1つの SQLite トランザクションで適用します。外部システムへの書き戻しまで含む整合性は別の設計事項で、ローカルのロールバックではソースに届いた変更を取り消せません。この実装の順序と失敗時の挙動は[前節](#失敗時のセマンティクスの詳細)で宣言しています。

強制されるルールは 1 つだけです。呼び出し側はランタイムをトランザクションで包めません。Action の実行と `load()` は、呼び出し側が開いたトランザクションの中では実行を拒否します。その中では「コミット済み」が実際には「呼び出し側が savepoint をロールバックするまで」を意味してしまい、適用と監査を終えたアクションが、成功報告の後に取り消せてしまうからです。これは原子性の保証であって、侵入への防御ではありません。

境界の残りは、防御ではなく宣言です。このランタイムはプロセス内ライブラリなので、データベースハンドルを握っているコード（呼び出し側、ルール、write-back アダプタ）は、直接 `UPDATE` を発行すればアクションゲートを迂回できます。プロセス内の検査でこれを防ぐことはできません。そこで契約として、ルールとアダプタはオントロジーストアに触れてはならない、と定めています。アダプタには触れる理由がそもそもありません。編集プランとターゲットオブジェクトの自分専用コピーを受け取り、話す相手はシステムオブレコードだけだからです。

強制力のある境界が必要な配備では、ランタイムをプロセス境界の向こう側に置き、消費者がデータベースへ直接アクセスできない構成にしてください。付属の MCP サーバーは、まさにその構成です。

## 保存できる値の境界

ストアは JSON を保持します。したがって、保存されるすべての値は、JSON への直列化と復元を無変更で通過しなければなりません。復元時に姿を変えるか脱落する値、たとえばクラスインスタンス、`Date`、`NaN`、`Map`、任意の深さの `undefined` を含む行は、アクション経由でも `load()` 経由でも、書き込みのたびに拒否されます。同じ検査を、`owned` プロパティの宣言済みデフォルトは定義時に、アクションの params は入口で受けます（前述の監査の項を参照）。

プロパティスキーマには、値を変換しない検証専用のスキーマを使ってください。これはモデル作者が守る契約です。ランタイムは保存済みの値を後の書き込みで同じスキーマに再度通すため、変換を行うスキーマ（`z.coerce.date()` や `.transform(…)`）は、次回の検証で自分自身の出力を拒否するか、気づかれないまま書き換えてしまいます。

## 再インデックスと編集

スナップショットのセマンティクスは、ロードされた型ごとに「ベースを置き換え、編集レイヤーを再適用する」です。個々の規則を、結果から先に示します。

- **拒否：ontology-owned な状態を供給するスナップショット行。** ontology-owned なプロパティに値を設定する行、ontology-owned な型の行、ontology-owned なリンクのインスタンスはすべて拒否されます。ソースはそのいずれの所有者でもないからです。
- **保持：ontology-owned なプロパティへの編集。** 編集は (type, pk) をキーとするオーバーレイに置かれ、再インデックス後、現在のパッチが新しいベースの上に再適用されます。宣言済みデフォルトへ戻された編集はオーバーレイから取り除かれます。編集を消すことは、それを保持する義務も消すということです（比較は構造的に行われるため、キーの順序で「デフォルトに戻った」ことを偽装することも隠すこともできません）。
- **そのまま保持：ontology-owned な型とリンク。** `load()` はそれらに触れること自体を拒否するので、オーバーレイは不要です。
- **丸ごと拒否：編集を取り残すロード。** ontology-owned な編集を抱えたベース行が消えるようなロードは全体が拒否され、以前の状態がそのまま残ります。その状態をどうするかは照合上の判断であり、ランタイムは照合上の判断を黙って下しません。編集をクリアするか行を復元してから、再ロードしてください。編集のクリア自体もアクションなので、照合作業も書き込みゲートの内側に留まります。
- **拒否：モデルがもう所有しないオーバーレイキー。** モデルが ontology-owned と宣言しなくなったプロパティをオーバーレイのパッチがまだ持っている場合、ロードは拒否されます。その状態の行く末を決めるのは明示的なスキーマ進化であって、リフレッシュではないからです。
- **拒否：制約を壊す部分スナップショット。** ロード対象外の型に残っている状態がモデルの制約に違反する場合、再インデックス全体が拒否され、ロールバックされます。

## 現在の制約

- 作成には write-back 前に確定した ID が必要です。ソースが採番した ID や、ソースから返された値の取り込みは未対応です。
- オブジェクトの削除・リンク属性・複合主キーは未対応です。関係に伴う数量や日時は、工場の出荷明細や金融の取引のように、独立したオブジェクトとして表せます。
- ネストしたプロパティの検証はその Zod スキーマに従い、ランタイムが strict にすることはありません。
- クエリはローカルの SQLite スナップショットを使い、ページングや結果件数の上限はありません。保存クエリ・遅延評価・自動的な経路履歴・再帰探索・任意の transform・結合・フェデレーション・実行時のスキーマ進化は実装した API の範囲外です。
