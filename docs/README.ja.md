# Operational Ontology

[![CI](https://github.com/gura105/operational-ontology/actions/workflows/ci.yml/badge.svg)](https://github.com/gura105/operational-ontology/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](../LICENSE)

> **Operational Ontology（操作可能なオントロジー）とは、外部システムのデータの上に構築する共有ドメインモデルです。オブジェクトとリンクによって業務の現在地を読み取り、アクションによって業務ルールを検証し、実行履歴を監査したうえで、変更をシステムオブレコード（基幹システム）へ書き戻します。**
>
> セマンティックレイヤーはビジネスを「読む」ためのもの。Operational Ontology はビジネスを「動かす」ためのもの。

<img src="./assets/hero-diagram.svg" alt="読み取りは共有モデルからエージェント・アプリ・人へ届く。書き込みは監査つきのアクションゲートを通り、状態を所有するシステムオブレコードへ書き戻される。">

このリポジトリは、Operational Ontology の概念を小さな TypeScript のリファレンス実装として具体化したものです。Palantir Foundry の Ontology から設計パターンを抽出し、コードを読んでフォークし、自身のプロジェクトへ応用できる形にまとめました。あくまで学習・参照用の実装であり、フレームワークや依存ライブラリ（npm パッケージ）として利用するものではありません。

## クイックスタート

Node.js 24 以降と pnpm が必要です。

```sh
pnpm install
pnpm demo    # 物理データ → 統合 → インデックス → 読み取り → 書き込み → 拒否 → 書き戻し
pnpm test    # 振る舞いの検証
```

デモは[このリポジトリの元になった記事](https://note.com/gura105/n/nfe927c169c6a)のシナリオに基づいています。企業買収によって**スキーマもステータス体系も異なる2つのレガシー受注システム**を抱えた企業を想定し、SQL とシンプルなマッピング処理でデータを1つのモデルに統合します。デモを実行すると、以下の動作を確認できます。

- リンクの走査と集計により、両システムを横断したクエリに答えられる。
- `cancelOrder` が出荷済み注文のキャンセルを拒否し、受理されたキャンセルのみ元の ERP へ書き戻す。
- `assignOrder` と `addOrderNote` がオントロジー独自のデータを保存し、再インデックスでソースデータが更新されても担当者とメモが失われない。
- 承認・拒否を問わず、すべてのアクション実行履歴が監査ログに記録される。

## なぜ Operational Ontology を定義するのか

「この顧客に未出荷の注文はいくつあるか」という問いに一貫した定義で答えるには、データを業務（ドメイン）の言葉で解釈するモデルが必要です。さらに、アプリケーションや AI エージェントが「その注文をキャンセルする」際には、操作の前提条件を検証し、実行履歴を記録したうえで、マスタデータを管理する ERP へ変更を反映する仕組みも欠かせません。この一連の責務を単一の共有モデルとして捉えることが、本リポジトリの出発点です。

単に「セマンティックレイヤー」や「オントロジー」と呼ぶだけでは、どこまでの責務を含むのかが曖昧です。周辺の概念と「何をモデル化するか」「業務操作をどう扱うか」という観点で比較すると、立ち位置が明確になります。

| 概念・構成 | 主にモデル化するもの | 業務操作との関係 |
| --- | --- | --- |
| セマンティックレイヤー | 指標・属性・集計の意味 | データへの問いに一貫して答える。操作の条件や書き戻しは別途設計する。 |
| 形式オントロジー・ナレッジグラフ | 概念の意味、エンティティと関係 | 意味や関係を表現する。データ更新に加え、業務ルールや監査をどう組み込むかは別途設計する。 |
| AI コンテキストレイヤー | 回答や判断に必要な意味・背景情報 | エージェントの理解を支える。実行する操作の統制は別途設計する。 |
| CRUD API・API ラッパー | データアクセスや個々の処理 | ルール・監査・書き戻しをどこで担保するかは、各 API の設計に委ねられる。 |
| **Operational Ontology** | **共有するオブジェクト・リンクと、ルールを備えたアクション** | **業務操作の条件・監査・管理元への書き戻しを、共有モデルの契約として定める。** |

これらの技術は互いに組み合わせて利用できます。本リポジトリで定義したいのは、**すべての利用者（UI・スクリプト・AI エージェントなど）が共通のモデルを介し、同一の業務ルールのもとで状態を変更するアーキテクチャ**です。Palantir Foundry の Ontology からこの設計パターンを抽出し、特定製品に依存せず議論・実装できるよう、次の4つの性質によって Operational Ontology を定義します。

## 4つの性質

本リポジトリでは、以下の4つをすべて満たすシステムを Operational Ontology と定義します。これらは設計パターンの核となる原則であり、具体的なストレージ、データ統合ツール、整合性保証の仕組みは各実装の選択に委ねられます。

1. **セマンティックなオブジェクトとリンク。** 外部システムが管理する既存データの上に、業務上のエンティティとそれらの関係を明示的にモデル化します。
2. **アクションに一本化された書き込み。** 業務上の意思決定に伴う状態変更は、すべて名前付きアクション（Action）を経由します。UI も AI エージェントも同じ API を利用します（※ソースデータの再インデックスは、これとは別のインフラ層の処理として扱います）。
3. **アクションに紐づく業務ルール。** 「出荷済みの注文はキャンセルできない」といった不変条件を事前条件（precondition）として検証します。違反時は機械可読なエラーを返して拒否し、承認・拒否の両方の試行結果を監査ログに記録します。なお、業務上の妥当性を検証するルールと、誰が操作できるかを制御するアクセス権限（認可）は別の関心事として分離します。
4. **システムオブレコードへの書き戻し。** 状態（データ項目）ごとに信頼できる管理元（所有権）を宣言し、外部システムが所有する状態の変更は、制御された副作用（write-back）として元のシステムへ反映します。実際にソース側の状態を書き換えるところまでが、このパターンの責務に含まれます。

デモでは、状態の所有形態を次の3種類に分類しています。

- **source-backed（ソース管理）：** `Order.status` は ERP が管理元であり、キャンセルの結果も ERP へ書き戻します。
- **ontology-owned（オントロジー管理）：** ソース側にカラムが存在しない担当者（`assignee`）やメモは、オントロジー自身がデータを所有します。
- **derived（派生値）：** 合計金額や件数はクエリ時に動的に計算し、永続化（書き込み）は行いません。

<img src="./assets/authority-map.svg" alt="Order オブジェクトの authority map。status と total は上流の受注システムが管理する source-backed で、統制された write-back 経路を通る。assignee と Note は ontology-owned で、オントロジー自身のデータストアで管理する。集計値や件数は derived で、計算されるだけで書き込まれない。所有者が宣言されていない状態は禁止。">

## コードで見るパターン

モデルは、オブジェクト型・リンク型・アクション型を定義したプレーンなデータ構造（値）です。この3種類の型定義には、それぞれ実行時のインスタンスが対応します。

| 定義（型） | 実行時のインスタンス |
| --- | --- |
| オブジェクト型：`Order` | 個々の注文データとそのプロパティ |
| リンク型：`customerOrders` | 特定の顧客と注文の紐づき |
| アクション型：`cancelOrder` | 特定の注文に対する1回のキャンセル実行 |

アクションが生成するオブジェクトやリンクへの変更内容は **Edit（編集プラン）** として表現され、承認・拒否を含むすべての実行履歴と結果は **監査ログ（Audit Log）** に記録されます。スキーマやルールの定義はコードとして管理し、インスタンスの状態や実行ログはデータストアに保持します。

また、「割当可能な設備を探す」といった定型的な業務クエリは、読み取り専用の **Function** としてモデル内に定義できます。これにより、各利用者が検索条件を個別に実装することなく、共通の業務ロジックに基づいた結果を取得できます。

モデルをクラスではなくプレーンなデータ構造で表現しているのは、実行時にモデルのメタデータを検査（イントロスペクション）できるようにするためです。たとえば `class Order { cancel() {} }` のようなメソッド定義だけでは、パラメータのバリデーション規則や事前条件を外部から抽出できません。データとして定義を持つことで、複数のアプリケーションから同一モデルを共有できるほか、実行時に構造を解析して MCP ツールを自動生成するといった処理が可能になります。

以下のコードは、キャンセルの事前条件をアクションのパラメータおよび変更内容（effects）とともに定義した抜粋です。import 文や全体の定義は [`examples/orders/ontology.ts`](../examples/orders/ontology.ts) を参照してください。

```ts
const objects = {
  Customer: defineObject({
    primaryKey: 'id',
    properties: { id: z.string(), name: z.string(), region: z.string() },
  }),
  Order: defineObject({
    primaryKey: 'id',
    properties: {
      id: z.string(),
      status: z.enum(['pending', 'shipped', 'cancelled']),
      total: z.number().int(), // minor units — 金額は浮動小数点（float）で扱わない
      assignee: z.string().nullable(),
    },
    owned: { assignee: null },                        // オントロジー自身が管理する状態であることを宣言
    source: 'north.tbl_order ∪ south.SALES_ORDER',    // 元となる物理データソース
  }),
}

const ontology = defineOntology({
  name: 'orders',
  objects,
  links: {
    customerOrders: defineLink({ from: 'Customer', to: 'Order', kind: 'one-to-many' }),
  },
  actions: {
    cancelOrder: defineAction(objects, {
      object: 'Order',
      targetParam: 'orderId',
      params: { orderId: z.string(), reason: z.string().min(1) },
      preconditions: [
        ({ object }) => object.properties.status === 'shipped'
          ? reject('SHIPPED_ORDER_CANNOT_BE_CANCELLED', `order ${object.pk} has already shipped`)
          : undefined,
      ],
      effects: ({ object }) => [modify(object, { status: 'cancelled' })],
      writeback: true,
    }),
  },
})
```

`execute('cancelOrder', …)` を呼び出すと、ランタイムは対象オブジェクトを読み込み、事前条件を検証します。条件を満たしていれば編集プランを検証したうえでソースシステムへ書き戻し（write-back）、ローカルの編集内容と監査ログをコミットします。`effects` 関数は「どう変更するか」を宣言的に記述するだけで、実際の外部システムへの書き込み処理はアダプタが担います。

<img src="./assets/action-gate.svg" alt="人間も AI エージェントも、同じ統制されたゲートを通って名前付きアクション cancelOrder を呼び出す。事前条件は出荷済み注文を機械可読なエラーで拒否し、適用された呼び出しはステータスを遷移させる。適用も拒否も、すべての試行が監査ログに残る。汎用の UPDATE 経路は設計上存在しない。">

## 適用例：データ駆動オペレーション

製品のリコール、設備の異常検知、入院の受け入れ調整、不正取引のアラート対応——。現場のオペレーションでは、発生した事象に対して複数の情報を突き合わせ、「誰に・何に対して・どの根拠で対応するか」を判断し、状況の変化に合わせて意思決定と実行を繰り返します。本リポジトリでは、こうした一連の業務フローを **データ駆動オペレーション** と呼びます。

注文デモ（`pnpm demo`）は、複数システムのデータを共通モデルに統合し、業務ルール・書き戻し・所有権・監査を組み合わせる Operational Ontology の基本構造を示しています。

次のステップとして、**リコール対応**の例を用意しています。同じ注文モデルにカスタマーサポートシステムを統合し、出荷済み注文から対象顧客を特定したうえで既存チケットと照合し、未対応分を新規起票します。注文は ERP、チケットはサポートシステムで管理されており、データの探索から業務アクションの実行までを一貫した流れで扱います。

さらに、工場・病院・金融のサンプルでは、影響範囲の追跡、候補の評価と割り当て、集合演算と集計を用いた調査へと応用範囲を広げています。

| 例 | 示す業務の流れ | 実行 |
| --- | --- | --- |
| [リコール](../examples/recall/README.ja.md) | ERP とサポートシステムを横断し、対象顧客の特定から交換対応チケットの起票までを辿る。 | `pnpm demo:recall` |
| [工場](../examples/factory/README.ja.md) | 製造・出荷の履歴から影響範囲を特定し、根拠とともに対応タスクを記録する。 | `pnpm demo:factory` |
| [病院](../examples/hospital/README.ja.md) | 病床と看護師の候補を評価し、組み合わせの制約条件を再検証して仮割当を記録する。 | `pnpm demo:hospital` |
| [金融](../examples/finance/README.ja.md) | 口座間の共通する受取先や取引パターンを調べ、根拠とともに調査ケースを記録する。 | `pnpm demo:finance` |

いずれも架空のデータを用い、集合の探索とモデルに定義された業務ルールを組み合わせています。対象候補や共通点が見つかっただけでは状態は変わらず、必ずアクションを通じて業務上の判断を確定・記録します。

## AI エージェント向け（MCP）

```sh
pnpm mcp     # 同じオントロジーを stdio 経由で公開
```

モデル定義から `search_order`、`traverse_customer_orders`、`cancel_order`、`read_audit_log` などの MCP ツールが自動生成されます。AI エージェントが出荷済み注文をキャンセルしようとすると、人間が操作した場合と同様に `SHIPPED_ORDER_CANNOT_BE_CANCELLED` エラーが返されます。業務ルールがモデル側に組み込まれているため、プロンプトによるルールの強制に頼る必要がありません。

リポジトリ内の [MCP 設定](../.mcp.json) を使って注文デモに接続できます。取得したデータのフィルタリングはエージェント自身のコード実行環境で行います。処理の流れと入力形式は[実装ノート](./IMPLEMENTATION.ja.md#mcp-のクエリ入力)、呼び出し元（actor）の扱いは[identity の説明](./IMPLEMENTATION.ja.md#可視性と呼び出し元の-identity)を参照してください。

## 実装の範囲と宣言

本リポジトリが実装しているのはアーキテクチャの「中間層」です。周辺のアプリケーションやデータ統合処理はデモ用に用意したものです。

担当者やメモのようにソースシステムに存在しない状態や、アクションの実行履歴は、この中間層で永続化する必要があります。そのため本実装は、ソースシステムからのスナップショットに加え、アクションによる編集内容と監査ログを保存する独自のデータストアを備えています。

<img src="./assets/where-this-sits.svg" alt="3 つの層 — アプリケーション、Operational Ontology、データ層 — をそれぞれ Foundry での実装とこのリポジトリでの実装に対応づけた図。このリポジトリが実装するのは中間層で、自前のストアを所有する。オントロジーとデータ層の継ぎ目には 2 つの契約がある：統合済みの物理データは与えられるものであり、書き戻しは統制された副作用である。">

呼び出し側から観測可能な設計上の選択（振る舞いの仕様）は、実装ごとに明示する必要があります。本リポジトリにおける仕様は以下のとおりで、実行時には `Runtime.declarations` からも参照できます。

| 項目 | 本実装における仕様宣言 |
| --- | --- |
| データの管理元 | `owned` と `writeback` で所有権を宣言し、生成された編集プランと照合する。 |
| 書き戻しの失敗時 | ソースへの書き戻しを先に実行する。ソース側が拒否した場合はローカルも変更しない。ソース更新後にローカルのコミットが失敗した場合は不整合が生じるため、照合（リカバリ）が必要になる。 |
| 再インデックス | ソース管理の状態は更新しつつ、オントロジー管理の状態は保持する。オントロジー側の編集データを欠落させるようなロード処理は拒否する。 |
| 可視性（アクセス制御） | ポリシー未設定のオブジェクトは全員に公開される。呼び出し元（actor）は自己申告制で認証機能は持たない。監査ログの読み取りは可視性フィルタのかからない管理者ビューとして動作する。 |

このランタイムは、同期的なアクション実行と SQLite を用いて設計パターンの最小構成を示しています。UI ビルダー、データパイプライン基盤、大規模インデクシング基盤、汎用的な認可システムなどは含みません。書き込みゲートも、呼び出し側と同一プロセス内における API レベルの契約として実装しています。このようにスコープを絞ることで、コード全体の見通しと読みやすさを保っています。

アクションは事前に指定した ID を用いて、`ontology-owned` なオブジェクトの作成や、`write-back` を介した `source-backed` なレコードの作成が可能です。一方で、削除操作・リンク属性・複合主キーには対応していません。その他の制約や API の詳細は[実装ノート](./IMPLEMENTATION.ja.md#現在の制約)にまとめています。公開済みのバージョンについては [release notes](https://github.com/gura105/operational-ontology/releases) を参照してください。

## FAQ

**これは単なる「バリデーション付き CRUD」では？**

構成要素自体は馴染みのあるものですが、アーキテクチャ上の責務が異なります。一般的な CRUD のバリデーションは、特定のアプリケーションの内部で、そのアプリが所有するテーブルに対して行われます。対して Operational Ontology では、外部システムが所有するデータの上にモデルを構築し、すべての利用者（UI・スクリプト・AI エージェント）で共有します。さらに、アクション以外の業務的な書き込み経路を遮断し、すべての試行を監査し、受理された変更をデータの管理元へ書き戻します。既存の概念で最も近いのは、「特定のアプリケーションから切り離され、他システムのデータの上に配置された CQRS のコマンド層」です。

**ナレッジグラフでも書き込みや更新はできるのでは？**

確かにデータの書き込みや条件付き更新は可能ですし、スキーマとインスタンスの両面も備えています。Operational Ontology がさらに踏み込んでいるのは、アクションの「型（業務操作の定義）」と「インスタンス（個々の実行履歴）」をモデルに組み込んでいる点です。名前付きの業務操作、機械可読な拒否理由、実行の監査証跡、システムオブレコードへの書き戻しを一体として扱います。違いは技術的な実現可否ではなく（トリプルストア上にこれらを構築することも可能です）、何がモデルのファーストクラス（第一級）の要素として定義され、共通のルールで統制されるかにあります。

**なぜ YAML ではなく TypeScript で定義するのか？**

業務ルールはコードそのものだからです。YAML に独自の式言語を埋め込むアプローチは、やがて場当たり的なルールエンジンへと肥大化しがちです。TypeScript のオブジェクトリテラルであれば、モデルのメタデータを検査可能なデータ構造として保ったまま、業務ルールを通常の型付きコードとして記述できます。「構造はデータ、ルールは関数」という役割分担です。
